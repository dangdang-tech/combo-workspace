Share the conversation you have already had with Codex, so another person can continue from that context. Creating an invitation saves the existing user and assistant text. Each invited Google account receives its own conversation; later messages stay with the person who sends them.

<Callout type="info" title="COMBO development version">
This page describes the COMBO source build. Its product policy allows shared session entries, session sharing, and content keys. Set `HAPPIER_FEATURE_SHARING_SESSION_ENTRIES__ENABLED=1` on the server; the server entry flag is off by default. Keep session sharing and content keys enabled as well. Use matching server, CLI, and UI builds; upstream Happier packages do not contain this behavior. Legacy direct-share and public-link routes are not part of this product surface. This page does not certify a deployed environment.
</Callout>

## What you need first

- Google-linked accounts on the same COMBO server. Self-hosters must configure [Google OIDC with keyed accounts](/self-hosting/auth-oidc#google-keyed-accounts-with-e2ee).
- An online host daemon, a working Codex configuration, and an owned session in the project directory you want to share.
- A source conversation whose history does not depend on a fork ancestor. A member's managed conversation cannot be shared again.
- On encrypted deployments, a per-session source key and the recipient's registered content keys. Restore or connect account keys before accepting an encrypted invitation.

## Shared workspace entries

1. Open your session's information screen and choose **Share conversation**.
2. Choose **Create invitation**, then **Copy invitation link**. The context is fixed when the invitation is created, even if the recipient accepts later.
3. The recipient opens the link. If it names another relay, choose **Continue on the invitation server**, then sign in with Google and choose **Accept invitation**.
4. Keep the host online while it prepares the conversation. The recipient can read the copied user and assistant text and send a new message that continues from it.

A returning recipient reuses their existing conversation. Different invited accounts receive different conversations. The host's later chat messages are not added to those copies, and a recipient's replies are not written into the host's original conversation.

### Project files remain shared

Every conversation uses the source session's project directory on the host machine. There is no workspace clone: file edits made from one conversation are visible to the others. Coordinate changes to the same files.

Model usage uses the host's Codex credentials and is charged to the host's account. Members can read and send messages in their assigned conversation. They cannot manage sharing or approve tool permissions. The host handles permission prompts under the Agent's existing execution policy.

### Encryption and copied context

On encrypted deployments, each child conversation has an independent data encryption key (DEK). The host decrypts the saved source text and encrypts the copied history for the child. The member receives access to the child's key, without receiving the source conversation's key or permission to read its later history. Plaintext deployments keep the same access rules with plaintext storage.

The copied context is readable user and assistant text. It does not reproduce tool payloads, reasoning traces, attachments, or the complete provider session. Codex receives this text through the existing replay mechanism when the member continues chatting; copying history does not submit the old prompts as new tasks.

## Limits

A saved entry holds at most 5,000 main-conversation storage rows and 2,000,000 bytes of serialized snapshot data. The host also applies its replay budget, which defaults to 120,000 characters including the prompt framing. A conversation that exceeds these bounds, cannot be decrypted completely, or relies on a fork ancestor is rejected. It is not silently replaced with a truncated tail or a newer live history.

Presence checks currently require a single API instance and the exact host's live connection. A disconnected host rejects new tasks. The UI keeps rejected input as a draft; send it manually after reconnection. Previously accepted tasks stop dispatching while the host is offline or access is disabled. An already running Agent is not guaranteed to stop when access is disabled.

Deleting the source session also deletes its sharing entry, memberships, and their stored access grants. This removes existing members' authorization as well as stopping new acceptance. Child conversations remain with the host. This does not promise an immediate disconnect of every open connection or erase already downloaded history; a saved entry is not an independent backup of a deleted source.

## Manage invitations and access

The host's member list shows **Can use** or **No access**. **Disable access** revokes ongoing access; **Allow access** restores the same conversation after the host prepares its grant again. This also restores an already allocated legacy child without importing new context. Re-enabling can make previously accepted, retained tasks eligible again. Revocation cannot erase history that a recipient has already downloaded.

Copy an invitation when it is created: the server stores its token hashed and cannot show it again. **Replace invitation link** creates a new token and invalidates the previous token for future acceptance. It preserves the entry's original context and its existing members. To capture newer context, choose **Create new sharing snapshot**.

Invitation links have no expiry or redemption limit. A forwarded link can be accepted by another eligible Google account. Replacing the link does not disable people who already accepted it; manage those members individually.

## When it goes wrong

**An older invitation has no saved context.** The host should create a new sharing snapshot for new recipients. Existing members and their conversations remain under their existing access rules, including revoke and restore. An invitation with existing members cannot be silently upgraded to the host's current history. An unused legacy entry can acquire its first snapshot when the host replaces its invitation link.

**The context is too large or unavailable.** Use a shorter, regular conversation with the necessary context. Fork ancestry, unreadable encrypted rows, and a snapshot beyond the host's replay budget are rejected before a new child is launched.

**The host cannot finish preparation after an upgrade.** Update the server, UI, and host CLI together. An older daemon cannot finish the updated preparation protocol. Keep the existing data directory and follow the deployment's database upgrade procedure.

**Encrypted access is not ready.** Restore or connect the recipient's account keys. A legacy encrypted source without a per-session key requires a new source session. If the host's account creation mode differs from the saved source mode, use a source in the current mode; the host will not downgrade an encrypted copy.

**A member cannot approve a tool request.** Approval belongs to the host. Changing the member's access switch does not delegate tool approval.
